# T3 Code 0.1.13 integration

Reviewed on **2026-11-26 UTC**. GitHub's latest stable release and npm's
`t3@latest` resolved to **0.1.13**, tagged at
`bc0f04da94f64b5e487c598761a43b4cf06b2ac9`.
[Upstream release](https://github.com/pingdotgg/t3code/releases/tag/v0.1.13)

## Runtime compatibility

- Basaltwater setup already selects the stable release. The standalone
  archive layout, service state protocol **4**, and compatibility with
  protocol **3** launchers during remote updates carry forward. Preserve
  upstream preflight and the private recovery copy when updating. The new
  launcher confirms an update's commit before removing its backup.
  [Launcher protocol](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/cloud/serviceProtocol.ts)
  · [Backup handling](https://github.com/pingdotgg/t3code/pull/42659)
- Database migrations **118** and **119** add workflow pools and run subjects.
  [Migration list](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/persistence/Migrations.ts)
- The pairing helper's 16 client permissions and owner-side
  `relay:configure` contract carry forward. For manual connection, the
  upstream background service now directs the operator to `t3 pair`.
  [Auth contract](https://github.com/pingdotgg/t3code/blob/v0.1.13/packages/contracts/src/auth.ts)
  · [Service guide](https://github.com/pingdotgg/t3code/blob/v0.1.13/docs/user/background-service.md)
- Recommended versions for Basaltwater's selected providers carry forward.
  Check the live provider catalog, executable, and account in the owning
  environment before relying on a specific model or feature.
  [Provider manifest](https://github.com/pingdotgg/t3code/blob/v0.1.13/apps/server/src/provider/model-manifest.json)

## Workflow changes

- **Workflow subjects and pools** support finding the run for an issue or
  PR, capping whole workflows, and sharing a bounded resource across
  workflows. The installed scheduling guidance covers queue inspection,
  recovery, and safe pool use.
  [Scheduling skill](../../../common/agent_skills/basaltwater-subagents/references/t3-scheduling.md#durable-workflows)
- **Local delegated worktrees** now support multi-repository projects,
  including plain project folders. Verify the branch and checkout of each
  repository. Cancelling worktree setup preserves a checkout shared by a
  side chat.
  [Orchestration skill](../../../common/agent_skills/basaltwater-subagents/references/t3-orchestration.md#workspace-ownership-and-retention)
  · [Setup cancellation change](https://github.com/pingdotgg/t3code/pull/43230)
- **Client controls** include full path copy, GBK and GB18030 file and diff
  rendering, and protection for existing prompts when the stash is full.
  In the Device panel, stop the intended simulator or emulator explicitly.
  Closing its tab ends streaming. Use **Stop all devices** only when all
  running devices in the listed scope can be stopped. SDK provisioning
  remains a [deferred plan](../../plans/mobile-agent-support.md).
  [Device stop change](https://github.com/pingdotgg/t3code/pull/43191)

## Verification

GitHub-digest-verified Linux x64 archives passed fresh 0.1.13 startup and a
0.1.12-to-0.1.13 restart in disposable homes. Both versions served HTTP
through Basaltwater's output filter. 0.1.13 passed embedded PTY and dotenv
probes, SQLite quick checks, and Basaltwater's read-only idle query. Its
preflight accepted the migration-117 database with protocols 3 and 4.
0.1.12 preflight refused the upgraded migration-119 database. A fresh npm
cache resolved the 0.1.13 CLI and its service-install command.

Basaltwater's pairing helper issued a one-use link, revoked the bootstrap
session, and established a browser session with all 16 intended permissions.
Repeating the exchange was refused. A disposable protocol 4 launcher started
and stopped the 0.1.13 server, and its startup output showed pairing directions
without a pairing URL or QR code.

Synthetic workflows reused their run IDs on duplicate starts and returned
the matching runs when filtered by subject URL. Separate trials queued a run
behind a whole-workflow cap and a named step pool. In both trials, the open
question and queue survived a restart, and answering the first run's
question released capacity for the next run.

See the [qualification matrix](../t3-qualification.md#stable-feature-qualification)
for systemd update and recovery, native clients and devices, provider turns,
and Connect scenarios.
